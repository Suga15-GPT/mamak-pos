## Findings, most severe first

### F1. A till that stops reading can crash the server when its stream's time runs out (Low; new)
- What goes wrong (src/routes/stream.js:34-47):
  - The new timer calls `res.end()` after `STREAM_MAX_MS` (:41).
  - The 25 s ping (:35) and the event subscriber (:34) are only removed when the request closes (:43-47).
  - If the till has stopped reading (Wi-Fi gone, a tablet asleep) and part of the stream has not yet left the server,
    `res.end()` cannot finish, so the request does not close.
  - The next ping, or the next event, then writes after `end()`. Node raises `ERR_STREAM_WRITE_AFTER_END` as an
    'error' event on the response. Nothing listens for it, so the process exits.
  - 7f2c50b never ended a stream, so this could not happen there.
- Reproduction (`wae_app.js` with `stall_client.py`):
  - Setup: ff92e19 runs as `node src/server.js` with `STREAM_MAX_MS` 12 s.
  - A Python client plays the till: it opens `/api/stream` with a 2 KB receive buffer and then reads nothing.
  - N menu events are published (about 72 bytes of stream each), the 12 s pass, then one more event.

  | Unread events in the stream | ff92e19 | 7f2c50b |
  |---|---|---|
  | 50, 100, 200, 400 | stayed up | — |
  | 800 (about 60 KB) | stayed up, 4 of 4 | — |
  | 1,600 (about 115 KB) | exited at the next event, 4 of 4: `Error [ERR_STREAM_WRITE_AFTER_END]: write after end`, exit code 1 | stayed up |
  | 1,600, and no further event | exited at the next ping, 25 s after the stream opened, 4 of 4 | — |
  | 3,000 | — | stayed up |

  - With this PC's default receive buffer (64 KB, which Windows grows), 1,600 unread events did not do it.
  - A till that keeps reading: 3,000 events, stayed up.
  - Sizing (`events_per_order.js`): an ordinary order puts 12 events, about 1.2 KB, on every stream. That order is
    three dishes on two stations, an add-on round, every ticket taken to served, then paid.
    - So 60–115 KB is what about 50–100 orders put on a stream, all within its 5 minutes and while that till reads
      nothing.
  - Limits:
    - Node 24 on Windows (the only Node on this PC). The shop's image is node:20-alpine in Docker, which I did not
      run.
    - How much Linux and Docker Desktop's port forwarding hold before the server's socket fills was not measured.
- What it costs the shop:
  - Every till loses the server until Docker restarts it (`restart: unless-stopped`; a few seconds). Requests in
    flight fail.
  - Unlikely, given the amounts above, but new with this commit.
- Suggested fix:
  - When the timer fires, do the close clean-up (clear the ping, unsubscribe) before `res.end()`.
  - Or skip writes once `res.writableEnded` is set.
  - A `res.on('error', () => {})` would also stop a stray write from taking the process down.

### F2. A screen that has received no event yet misses an order placed in its reconnect gap (Low; new)
- What goes wrong (public/js/state.js:129, src/lib/events.js:36):
  - The page asks for `?since=` only once it has seen an event. `lastSeq` starts at 0 when a screen loads, and each
    update reloads every screen.
  - With no `?since=`, the server replays nothing (`if (!sinceSeq) return []`).
  - Since ff92e19 every stream ends after 5 minutes, and the page is away for about 1 s (1,004–1,021 ms measured).
  - An event in that second reaches the other screens, but not this one. It shows at the screen's own refresh: the
    Kitchen board every 30 s (kitchen.js:219), the POS every 60 s (main.js:61).
  - main's page reconnects the same way.
  - From the code (not measured): after a restart the server counts events from 1 again (events.js:11). A screen that
    has seen no event since the restart has the same gap.
- Reproduction:
  - `gap_zero.js`: each trial opens a fresh screen, waits for its stream to end (`STREAM_MAX_MS` 8 s), then has
    another till place an order 4–568 ms after the end.

    | Screens | Through the stream | Only at the screen's refresh |

    | ff92e19, the POS floor | 0 of 5 | 5 of 5, after 51.5–52.0 s |
    | ff92e19, the Kitchen board | 0 of 5 | 5 of 5, after 21.5–22.0 s |
    | ff92e19, one event first (`?since=3`), floor and board | 6 of 6, in 1.0–1.3 s | 0 |
    | main's page, the POS floor | 0 of 5 | 5 of 5, after 50.5–51.0 s |
    | main's page, the Kitchen board | 0 of 5 | 5 of 5, after 20.4–20.9 s |
    | 7f2c50b (its stream does not end), at the same moment, floor and board | 4 of 4, in 344–355 ms | 0 |

  - The soak in `stream_end.js` (the 5-minute default, two screens, an order placed just after one screen's stream
    ended, 4 times):
    - ff92e19's till had not yet received an event, because every order fell in its gap. It reconnected without
      `?since=` each time and showed none of the 4 within 15 s.
    - Its Kitchen board, which had seen one, reconnected with `?since=3` and `?since=5` and got all 4 (290–1,280 ms).
    - On main's page both screens missed all 4.
- What it costs the shop:
  - An order shows on one screen up to 30 s (Kitchen) or 60 s (POS) late.
  - That needs the order to land in that screen's 1-second gap before the screen has seen any event: the first order
    after the screens load, or after a restart.
  - Nothing is lost on the server. A pay screen stays safe: the server refuses a pay-in-full whose total no longer
    matches what the screen showed (`expected_due`, src/services/billing.js:242).
- Suggested fix:
  - Send the current event number when a stream opens (for example a small `hello` event the page stores as
    `lastSeq`), so every reconnect carries `?since=`.
  - Or have the page refresh its screen once after any reconnect. That also covers a restart.

  - Only the throwaway Postgres at localhost:5434. Every script refuses any other address.
  - The review folder was fast-forwarded to ff92e19 (`git merge --ff-only`) and ran it.
  - Controls on 7f2c50b and main (d947fab), and on e8e7222 and d5a9b4b for 022, came from `git archive` in my scratch
    folder.
  - Every schema came fresh from its tree's migrations. There is no new migration (`git diff 7f2c50b ff92e19 --
    migrations` is empty).
  - Gemini was a local stand-in.
- Time zones: everything ran in Malaysia time, as docker-compose runs the app. The tile cases, expense races,
  decimals and nits ran again in UTC.
  - The date-sensitive scripts ran after midnight shop time on 2026-10-03; none ran across midnight.

  - Node 24.19; the shop's Docker image is Node 20, which I did not run.
- Connections: counted with `netstat -an` (ESTABLISHED to the server's port), with no proxy.
- `STREAM_MAX_MS`:
  - The default (5 minutes) for the update runs and the 50-minute soaks.
  - 20 s, 15 s, 12 s and 8 s where said.
