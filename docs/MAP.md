# Codebase map

**Read this instead of exploring.** Every prompt in `docs/prompts/` names the files
it needs; this file tells you what is in them and roughly where. Keep it accurate —
every phase updates the rows it touches.

**Design rule already in place — preserve it:** `order_items` and `order_item_mods`
snapshot `name` and `price_cents` at order time. Editing or deleting a menu item
never rewrites a historical bill. Every new table must follow the same principle.

**Fixed in phase 05b** (was: "known edge case, not guarded" in phase 05): voiding a
line or applying a discount could push `amountDue` negative when the order already
had a payment recorded. Both now preview the resulting total first
(`billing.guardAgainstShortfall`) and refuse with `409` rather than allow it; if the
new total lands exactly on what's already paid, the order settles instead
(`billing.settleIfMatchesPaid`).

**Fixed in phase 09** (audit #22): `routes/reports.js`'s `/api/summary` month/year bucketing
compared a local (tz-naive) `paid_at AT TIME ZONE 'Asia/Kuala_Lumpur'` timestamp against a
boundary value cast to `::timestamptz` — that cast reintroduces a timezone (the DB session's,
not KL), which can shift a payment made near midnight KL into the wrong month. Fixed by keeping
every side of the comparison a plain (tz-naive) `timestamp`.

**Fixed in phase 12** (documented as a known limitation in phase 09): a Z report's sales side
was scoped by `orders.shift_id` (opened-in) while its cash side was scoped by `payments.shift_id`
(settled-in) — an order spanning a shift change (a mamak trading past midnight, which is most
nights, not an edge case) put its sale in one report and its cash in the next, making "gross
sales" and "payments received" disagree for no real reason. Fixed by adding `orders.closed_shift_id`
and moving every sales-side figure onto it, so both sides of the report are scoped by the same
"shift that actually settled this" concept by construction.

## Conventions in the existing code

- `awaitH(fn)` wraps an authenticated route; `publicH(fn)` wraps a public one and
  hides internal error text. Thrown errors carrying `.status` become that response
  — throw them via `AppError(message, status)` (`src/lib/errors.js`).
- Auth is plain Express middleware: `router.get('/path', requireRole('admin'), awaitH(...))`.
  **(Phase 11)** `requireRole(...roles)` (`src/lib/auth.js`) reads the session id from the
  httpOnly cookie (not a bearer token), 403s if the role isn't in the list, and — for every
  method but `GET`/`HEAD` — also requires a matching `X-CSRF-Token` header (`csrfOk()`, a
  `crypto.timingSafeEqual` compare against the token stored on the session). It further 403s
  with `{error: 'pin_change_required'}` if the user's `must_change_pin` is set, except on the
  two routes that must stay reachable to clear it (`POST /api/me/pin`, `POST /api/logout`).
  Pass no roles to just require *a* session.
- Money is integer cents in the DB; `cents2rm`/`rm2cents` (`src/lib/money.js`)
  convert at the edges only.
- Client-side, every string rendered into HTML goes through `esc()` (`public/js/state.js`
  on the staff app, `../js/state.js` re-imported on the customer page). Dynamic
  markup uses `data-action`/`data-id` attributes plus one delegated `click` (or
  `change`) listener per container — never an inline `onclick`/`onchange`.
- Shared staff-app state (`menu`, `tables`, `cart`, `selTable`, `activeCat`, …) lives
  in the single `state` object exported by `public/js/state.js`; import and mutate
  `state.foo`, don't reassign a destructured local.
